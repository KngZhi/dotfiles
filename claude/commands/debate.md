# Multi-Model Deep Debate

**Topic:** $ARGUMENTS

使用本地 CLI 工具进行多模型深度辩论，自动执行全流程。

---

## 执行指令

**严格按顺序自动执行以下流程，不要等待用户确认：**

1. 解析参数，确定模式（full/quick/deep）
2. 执行 Stage 1（4 人并行，含 Linus）
3. 分析共识度，决定是否进入 Stage 2
4. 执行 Stage 2（Linus 质疑所有人）
5. 执行 Stage 3-4（主持人追问 + 立场更新）
6. 输出最终报告
7. 询问是否归档

**quick 模式只执行：Stage 1 → Stage 2 Round 1 → Stage 6**

---

## 模式说明

```bash
/debate [议题]              # full 模式：完整流程（4 人辩论）
/debate quick [议题]        # quick 模式：Stage 1 + Round 1 + 总结（只保留两轮）
/debate deep [议题]         # deep 模式：增加多轮交锋 + Linus 红队挑战
```

---

## 角色设定

| 角色 | CLI | 调用方式 | 视角 | 风格 |
|------|-----|----------|------|------|
| **Codex** | `codex` | 直接调用 | 架构师 | 务实、权衡导向 |
| **Gemini** | `gemini` | 直接调用 | 通盘调查 | 全局扫描、风险识别 |
| **Claude** | `claude` | 直接调用 | 实现者 | 结构化落地、细节清晰 |
| **Linus** | `claude` | `Invoke the linus-code-reviewer agent` | **自由派/批判者** | **毒舌、直接、质疑一切** |

> **Linus 角色说明**：
> - 使用 `claude` CLI，但在 prompt 开头加入 `Invoke the linus-code-reviewer agent` 来激活 Linus 人设
> - 模仿 Linus Torvalds 的代码评审风格：直接、毒舌、不留情面
> - **全程参与辩论**，不是最后的评判者，而是第四个有立场的辩论者
> - 专门负责：质疑问题本身、找过度设计、推崇简单直接的方案

## Stage 1: 差异化分工（4 人并行）

利用各模型特长，从不同角度分析：

```
# 并行调用 4 个角色，注意各自的分工不同

mcp__pal__clink(
  cli_name="codex",
  prompt="[议题]

作为【架构师】视角分析（重要约束）：
1. 只做架构权衡，**禁止伪代码/实现细节**
2. 至少给出两套可行方案，并明确推荐其一
3. 写清楚取舍依据与放弃另一个方案的理由
4. 默认中等规模场景，优先最小化设计、可交付性优先"
)

mcp__pal__clink(
  cli_name="gemini",
  prompt="[议题]

作为【通盘调查】视角分析：
1. 从性能、稳定性、安全、运维、成本做快速扫描
2. 指出关键风险与信息缺口（无数据则明确假设）
3. 推荐哪个方案？为什么？"
)

mcp__pal__clink(
  cli_name="claude",
  prompt="[议题]

作为【实现者】视角分析：
1. 推荐哪个方案？
2. 具体实现复杂度与落地风险？
3. 给出高层实现步骤/模块拆分（**禁止写代码/伪代码**）"
)

mcp__pal__clink(
  cli_name="claude",
  prompt="Invoke the linus-code-reviewer agent.

[议题]

以 Linus Torvalds 风格自由分析这个议题：
1. 这个问题本身值得讨论吗？还是在解决错误的问题？
2. 你推荐什么方案？为什么？（越简单越好）
3. 有什么明显的坑是大家容易踩的？
4. 如果让你来做，你会怎么用最少的代码解决？

风格要求：直接、毒舌、不留情面。如果觉得问题本身就是扯淡，直接说。",
  continuation_id="debate_linus"
)
```

**Stage 1 完成后，提取并展示：**
- 各方推荐的方案（4 个角色）
- 核心论点（每方 2-3 条）
- 初步共识度评估（高/中/低）
- **Linus 的特别关注点**（他质疑了什么）

---

## 共识度检查（自动判断）

```
共识度判断标准（4 人辩论）：
- 高（>75%）：四方推荐同一方案，论点相似 → 跳到 Stage 3
- 中（50-75%）：三方一致或论点有交集 → 正常进入 Stage 2
- 低（<50%）：明显分歧或 Linus 强烈反对 → 进入 Stage 2 + 额外一轮

注意：如果 Linus 认为问题本身就是错的，共识度自动降为"低"
```

## Stage 2: 多轮交锋

### Round 1: 交叉质疑（并行，quick 模式仅执行此轮）

```
# 原有的交叉质疑

mcp__pal__clink(
  cli_name="gemini",
  prompt="Codex（架构师）推荐 [方案A]，理由是 [论点]。
  
作为通盘调查者，你如何评价？
1. 这个架构选择在性能/稳定性/安全/运维/成本上有什么影响？
2. 有没有被忽略的系统性风险？
3. 你是否改变立场？",
  continuation_id="debate_gemini"
)

mcp__pal__clink(
  cli_name="claude",
  prompt="Gemini（通盘调查）提出关键风险：[风险列表]。

作为实现者，你如何评价？
1. 哪些风险是可落地规避的？如何规避？
2. 哪些是过度担忧或可以延后？
3. 你是否改变立场？（**禁止写代码/伪代码**）",
  continuation_id="debate_claude"
)
```

### Round 1.5: Linus 质疑所有人（并行执行）

```
mcp__pal__clink(
  cli_name="claude",
  prompt="Invoke the linus-code-reviewer agent.

其他三位的观点总结：
- Codex（架构师）推荐：[方案和理由]
- Gemini（通盘调查）推荐：[方案和理由]
- Claude（实现者）推荐：[方案和理由]

现在逐一质疑他们：

1. **对架构师**：他的架构取舍是务实还是在逃避现实约束？哪里在过度设计/过度简化？

2. **对通盘调查**：他的风险清单是基于事实还是在吓唬人？有没有忽略更关键的问题？

3. **对实现者**：他的落地路径是不是过于复杂？有没有更简单的做法？

4. **总体评价**：这三个人有没有在『互相吹捧』？他们是不是都在回避真正的问题？

不要客气，有问题就直说。用具体的技术论据支撑你的批评。",
  continuation_id="debate_linus"
)
```

### Round 2: 回应质疑（如有必要）

```
# 只有当 Round 1/1.5 出现重大分歧时才执行

mcp__pal__clink(
  cli_name="codex",
  prompt="Gemini 和 Linus 对你的架构方案提出质疑：

Gemini 的质疑：[质疑内容]
Linus 的质疑：[质疑内容]

请回应：
1. 承认哪些问题是合理的？
2. 反驳哪些质疑？
3. 是否调整方案？",
  continuation_id="debate_codex"
)

mcp__pal__clink(
  cli_name="gemini",
  prompt="Linus 对你的通盘调查提出质疑：[质疑内容]

请回应：
1. 他说得对吗？
2. 你的分析依据是什么？
3. 是否调整立场？",
  continuation_id="debate_gemini"
)

mcp__pal__clink(
  cli_name="claude",
  prompt="Linus 对你的实现方案提出质疑：[质疑内容]

请回应：
1. 实现是否可以更简化？
2. 你坚持当前实现思路的理由？
3. 给出更简洁的落地步骤（如果 Linus 说得对，**禁止写代码/伪代码**）",
  continuation_id="debate_claude"
)
```

## Stage 3: 主持人追问（动态生成）

**不要使用固定问题列表，而是根据前面的讨论动态生成追问：**

```
mcp__pal__clink(
  cli_name="claude",
  prompt="作为辩论主持人，回顾整个讨论（4 位参与者）：

Codex（架构师）: [立场和论点]
Gemini（通盘调查）: [立场和论点]  
Claude（实现者）: [立场和论点]
Linus（批判者）: [立场和论点，特别是他质疑了什么]

请分析：
1. 四方都忽略了什么关键问题？（至少找出 3 个）
2. Linus 的批评有道理吗？其他三人应该如何回应？
3. 有没有第五种更好的方案没被提及？
4. 在什么边界条件下，当前推荐方案会失败？
5. 从用户/业务角度，还有什么没考虑到？
6. 如果必须在『简单但可能不完美』和『完善但复杂』之间选择，应该选哪个？"
)
```

3. 关键取舍与边界条件是什么？",

2. 最终推荐方案是什么？
3. 给出更稳的落地步骤/关键里程碑（**禁止写代码/伪代码**）",

## Stage 5: Linus 红队挑战（仅 deep 模式）

**在 deep 模式下，Linus 会进行额外一轮红队挑战，尝试攻破当前的共识方案：**

```
mcp__pal__clink(
  cli_name="claude",
  prompt="Invoke the linus-code-reviewer agent.

当前共识方案是：[方案]

进入红队模式，你的任务是摧毁这个方案：

1. **致命缺陷**：这个方案最可能在哪里爆炸？不是『可能有风险』，是『一定会出问题』的地方。

2. **恶意攻击**：如果我是一个恶意用户/开发者，我会怎么利用这个设计的漏洞？

3. **规模崩溃**：当数据量/用户量增长 100 倍，这个方案还能活吗？

4. **更简单的方案**：有没有一个方案简单到让当前讨论显得可笑？

5. **现实检验**：三个月后的半夜三点，这段代码会不会让 on-call 的人想骂娘？

用最刻薄的方式指出问题，但要确保每个批评都有具体的技术依据。",
  continuation_id="debate_linus"
)
```

## Stage 7: 归档（可选）

**辩论结束后询问用户：**

```
辩论完成。是否将结果归档为 ADR？(y/n)
```

如果用户确认，生成 ADR 文件：

```markdown
# ADR-[序号]: [议题标题]

## Status
Accepted | [日期]

## Context
[议题背景，为什么需要做这个决策]

## Decision Drivers
- [驱动因素 1]
- [驱动因素 2]

## Considered Options
1. [方案 A] - Codex 推荐
2. [方案 B] - Gemini 推荐
3. [方案 C] - Claude 推荐

## Decision
选择 [方案]，因为 [理由]。

## Consequences
### Positive
- [好处 1]

### Negative  
- [风险/代价 1]

### Risks
- [风险 1]: [缓解措施]

## Debate Summary
[链接到完整辩论记录或简要总结]
```

保存到: `docs/decisions/adr-XXX-[议题].md`

---

## 核心原则

1. **clink 省钱** - 调用本地 CLI 不走 API
2. **4 人差异化分工** - Claude/Gemini/Codex 各司其职，Linus 全程质疑
3. **Linus 是参与者** - 不是最后的评判者，而是从头到尾参与辩论的第四人
4. **保持 continuation_id** - 让讨论有上下文延续性
5. **主持人追问是灵魂** - 动态生成，不用固定列表
6. **智能路由** - 根据共识度决定流程深度
7. **结果可追溯** - ADR 归档供未来参考

---

## 快速参考

| 模式 | 流程 | 适用场景 |
|------|------|----------|
| quick | 1（4人）→ 2（Round 1）→ 6 | 简单决策，快速获取多方意见 |
| full | 1（4人）→ 2（含 Linus 质疑）→ 3 → 4（4人）→ 6 | 常规技术决策 |
| deep | 1（4人）→ 2（多轮）→ 3 → 4（4人）→ 5（红队）→ 6 | 重大架构决策 |
