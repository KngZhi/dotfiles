# Triage

Use the project's tracker and label conventions. Without a configured vocabulary,
inspect existing labels and propose the minimal mapping needed; installing another
skill is not a prerequisite.

For a queue inspection, show actionable items with a short reason. For a named
issue or PR, read its request, discussion, prior decisions, and relevant code.
Check whether the behavior exists or was previously rejected, then verify the
reported problem using the available evidence.

Distinguish bug from enhancement and unresolved from ready, blocked, or rejected.
Use configured states rather than imposing new names. Ask only when the requested
transition leaves a material ambiguity; a clearly authorized state change needs
no repeated approval.

When a brief is needed, read [AGENT-BRIEF.md](AGENT-BRIEF.md). Consult
[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) when recording a substantive rejection.
Preserve known facts and avoid re-asking resolved questions.

Publish comments, change labels, or close items only when applying that outcome is
part of the user's request. Prefix generated triage comments with:
> *This was generated by AI during triage.*

Verify the resulting item state. If an external step fails, retain the existing
item and resume that step rather than creating a duplicate.
