# Rejected Feature Records

Use the project's existing decision records, or .out-of-scope/ when that convention
is already in use, to preserve a substantive rejection. Group by concept and record
the reason plus links to relevant requests.

Search for relevant decisions when reviewing a similar request. Read the matching
records rather than loading the entire archive. A prior rejection is evidence;
reconsider it when the user or new facts change the decision.

Record an enhancement rejected on scope or design grounds. An already implemented
feature is not a rejection, and a temporary lack of time is a deferral.

Update records and close issues only within the requested triage outcome. Preserve
history when a decision changes; a superseding note is often more useful than
deleting the earlier rationale.
