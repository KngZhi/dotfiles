# Wayfinder

Use a map when an effort has enough unresolved, dependent decisions to benefit
from persistent tracking. If the route is already clear, produce the useful plan
directly and continue the user's authorized workflow.

Agree on the destination and scope from the existing request, asking only about
material unknowns. Planning produces decisions; execution belongs in the map
only when the user included it.

## Map and tickets

Use the configured issue tracker and its native parent/blocking relationships.
If none is configured, a local Markdown map is sufficient; setup is optional.
Name tickets by the question or outcome, and use descriptive links.

Keep the map as an index containing the destination, decisions with links, open
questions, and out-of-scope work. Store detailed evidence on each ticket.
Create only tickets that can be stated meaningfully now.

A ticket may need research, a prototype, a user decision, or a prerequisite task.
Use available research tools directly; specialized skills are optional aids.
Consult relevant project terminology and decisions without requiring another
domain-modeling skill.

## Work the frontier

Choose an unblocked ticket within the requested scope. Coordinate ownership when
other people or agents are working on the map. Gather evidence or the necessary
user decision, record the result, and update the remaining dependencies.

Continue to the next useful unblocked ticket while authorization and information
permit. A session boundary is not a completion condition. Stop at the requested
destination or a concrete decision/access blocker, keeping the map current.

Respect existing authorization for tracker writes and external communication.
A request to inspect an existing map alone does not authorize modifying it.
