# 客户销售下单

把用户已定的客户、货号和数量录入 K2046 客户销售单。来源可以是微信、WhatsApp、图片或用户直接给出的清单。采购单和 VRO 转到对应技能。

默认订单备注为空。用户明确要求备注时才填写；来源、识别过程、价格解释和技术标识留在任务证据中。草稿和完成汇报无需备注栏。

## 固定步骤：按顺序运行 CLI

1. 取数。微信先运行 `wechat` 的自检，再按群、日期和发送者读取消息或附件。WhatsApp 用现有可用来源；直接给出的清单可直接整理。保留用户最后一次更正，图片中的数量需结合显示单位读取。
2. 按 [planning.md](references/planning.md) 查客户、精确 SKU、包装、历史单位与价格、正常销售仓及库存。查询只读，原始结果放任务私有目录。
3. 完整读取该客户本日及未完成销售单，逐个回读疑似重复单；检查临时明细，见 [create-and-verify.md](references/create-and-verify.md)。已有同一订单时回报现有结果，不再建单。
4. 整理明确的客户和逐行数量、单位、单价、金额。文本输入用纯 `--preview` 验证解析；混合包装用显式 JSON。`--no-commit` 会真实建单，不能用来预览。
5. 在用户要求的范围内创建一次。默认省略 `--memo`，不填来源备注，不沿用旧临时单的备注或明细。创建后立即 `sale get`，再对本日及未完成范围完整分页 `sale list` 回读，核对客户、所有明细、包装、销售仓、价格、总额、备注及正式保存状态。
6. 已批准价格被写成零等写入偏差，按创建回读参考修正本次新单并重新回读。不确定写入是否成功时先查现有结果，再决定下一步。

## 判断与停点

- 用户已经看过清晰的货号、数量和单位，随后说“对的，帮我下单”，就是该草稿的确认。继续执行，不重复索取许可。
- 缺客户身份、数量单位或价格时，先从已有资料和相关历史查证；仍缺失时只问缺失的数据。相似客户或模糊 SKU 不能取第一个命中。
- 销售仓与 lazon 库存分别报告。lazon 有货不能证明销售仓有货。按客户历史和现有正常流程确定仓位，不自行换仓、调拨或改可售状态。
- 对实际库存异常、系统拒绝或不可售状态，按当前流程与用户已授权范围处理；尚未明确的业务处理才交给用户判断。不机械增加第二次库存确认，也不把个别负库存订单当作普遍忽略库存的规则。
- 临时明细有混入风险时先查明归属。保留他人的草稿；不得为了新单批量清理临时单、删除重复候选或修改已有业务单。
- 本技能只创建销售单；付款、发货、调拨、改商品状态和发送消息分别需要相应任务指令。

## 汇报

草稿说明客户、货号、数量及单位、单价和合计。完成后给客户、单号和 ID、逐行数量、总额及实际状态；有影响执行的异常单独写明。无需自动生成 PDF 或备注栏。
