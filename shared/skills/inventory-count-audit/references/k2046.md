## 盘点 DTO 会丢掉关键身份

本次客户端的 `stockChecks.getDetails` 返回 `sku / warehouseId / before / after`，其中 sku 来自原单 `productNumber`，可能仍是旧货号。原始响应则保留：

- `id`：明细 ID，用来去重；`stockCheckId`：单头 ID。
- `productId`：稳定商品身份；`product.id` 应与它一致。
- `productNumber`：单据历史货号；`product.productNumber`：当前商品货号。
- `warehouseId`、`oldNumber`、`newNumber`、`status`。
- `box / bigBag / bag / unit`：记录的包装输入，帮助区分总数与箱数。

优先获取保留商品 ID 的原始明细。已有客户端投影不足时，可在一次性只读调查中通过客户端可配置 transport 观察业务响应，方法仍调用稳定客户端；只保存响应业务字段。产品化的缺字段修复按仓库 API 工作流实施。仅有旧 SKU 时，从含商品 ID 的历史入库等明细建立已证实别名映射，未证实的别名保留为未匹配。

## 复用匹配工具

`scripts/match_stockchecks.py` 不联网、不改库存，只验证原始盘点数据并按商品 ID 筛选、汇总当前有效调整。先准备：

- `products.json`：目标商品数组，每行有整数 `id` 和当前 `productNumber`。
- `checks.json`：`{"headers": [...], "details": [...]}`，包含上述原始单头和明细。单头需有 `id / checkId / status / temp / detailsCount`；明细需有 `id / stockCheckId / productId / warehouseId / oldNumber / newNumber / status`，并保留历史 `productNumber`。
- `details` 可以来自全系统扫描或已按稳定商品 ID 选出的范围。工具只声明实际传入行数；完整性仍由分页记录证明。`--require-complete-details` 用于传入每张单的完整明细时，对照单头 `detailsCount`；已筛选明细不能使用此选项。

从该技能目录执行：

```sh
python3 scripts/match_stockchecks.py \
  --products /path/to/products.json \
  --checks /path/to/checks.json \
  --output /path/to/matched-checks.json
```

工具拒绝缺失商品 ID、重复明细、嵌套商品 ID 冲突、未知状态、单头明细状态冲突、空白或非有限数量。已删除记录需要单独调查，不按普通有效行计入。输出新旧货号、单号、前后数量和按商品/仓库汇总的调整。数量以十进制字符串保存，单位沿用输入的库存基本单位；工具不猜箱规或换单位。

当前 `Checked` 且非草稿的行计入调整，`NotChecked` 和草稿保留但不计入。这是当前状态复算口径，不证明历史上从未执行。工具不负责重建取消操作，不能把重复累计的盘点绝对数当增减量。

## 线上清单核对

若用户给的是 order-printer 的 `/conteo/revisar/…` 链接，读取该批次并保存提交时的系统数，不直接用现在库存替换。2026-10-12 核对的实现中：

- 按 lazon 的非零库存生成清单，负库存行自动预填零。
- 数量为 `箱 × packingBox + 打 × packingBigBag + 散件`，服务端再次计算。
- 审核目标为 `当前库存 + (填报实盘 − 提交时系统数)`，负目标按零处理并提示。

这些是当时版本的行为，未来检查应重新确认。真实数据演算能验证本批目标；生产审核是否已成功，仍需授权执行后的 K2046 读回。单据里存的 301 和程序把 1 箱算成 1 条是两种不同证据，前者不能证明后者。
