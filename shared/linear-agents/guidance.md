# Linear Agent guidance（Enginer 团队）

贴到 Linear：团队 Enginer → Settings → Agents → Additional guidance。
这份文件是它的版本记录；改这里再贴过去。

---

## 交付

- 小步提交，每次提交后立刻推送；分支从仓库默认分支开出，或从 issue 指定的分支开出。
- 以 draft PR 交付，正文写 `Fixes ENG-<编号>`；不要合并。
- 一个 PR 的改动约 300 行以内（不含测试、文档、锁文件）；做不到就停下来，在 issue 里说明并建议拆分。
- 写代码的 agent 不审自己的代码；审查只报告阻塞项 / 非阻塞项，不改代码、不提交。
- 完成时附「验收证据」：按 issue 的验收标准逐条写三样——(1) 你声称达成了什么；(2) 别人怎样独立核实（命令、URL、截图、文件与位置、查询、对照来源，任选合适的）；(3) 你实际核实到的结果，贴原文不转述。代码用可重跑的检查和真实输出；界面用截图；文档和数据用改动位置与对照来源；配置和部署用可观察的状态。无法独立核实的条目要明说，并指出人该看哪里。审查方会逐条复核。
- 开出 PR 后不要立刻结束：用 `gh pr checks --watch`（最多等 20 分钟）等 CI 跑完；有失败就读日志、修复、推送到同一分支，再等一轮；CI 全绿或确认失败与本次改动无关时才结束，并在回复里写明 CI 的最终状态。
- 遵守仓库里的 AGENTS.md；它和这里冲突时以仓库为准。
- 需要浏览器（验证页面、截图、复现界面问题）时用 `agent-browser` 命令行；不要用 Codex 自带的 "Browser use"，它在无人值守时会被自动拒绝。

## 写 issue / 评论

- 引用 GitHub 一律写完整 URL 或 `GH-N`，不写裸 `#N`（工作区的 GitHub 集成会把它链到错的仓库）。
- 作者才能决定的取舍（产品行为、范围、公开接口、数据语义、不可逆操作的边界）不要猜：列成问题，停下来等回复。
- 仓库里的既有约定、测试和现有行为能决定的细节，自己决定并在回复里注明"假设"。

## 可派发的标准（分诊时逐条核对）

1. 目标一句话说清做什么、不做什么。
2. 每条验收标准都能独立核实：写明看什么、怎么看（命令、URL、截图、文件位置、查询、对照来源）、看到什么才算达成。
3. 一个 PR 装得下（≤300 行）；装不下先拆，每个子 issue 再过这张表。
4. 没有未决的作者决定项。
5. 仓库明确（issue 挂在对应项目），写明要动的模块。
6. 写明交付时要贴的证据。
