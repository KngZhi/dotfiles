# Linear agents (Cyrus)

Two Linear agent identities, **Codex本机** and **Claude本机**, run on this
machine as two instances of [Cyrus](https://github.com/cyrusagents/cyrus)
(docs: <https://atcyrus.com/docs>). Delegating a Linear issue to one of them
opens a git worktree for the issue's repository, runs Codex or Claude Code in
it, streams progress into the issue's agent session, and ends with a pushed
branch and a draft pull request. Replying inside that session continues the
same agent conversation.

What this directory owns: the pinned runtime (`runtime/`), the routing and
label configuration (`config.template.json`), the launchd entrypoints
(`run.sh`, `service.sh`) and the deploy script. Nothing here is secret.

## Layout on the machine

| Path | Content |
| --- | --- |
| `~/.local/share/linear-local-agents/runtime/` | `npm ci` of `runtime/package-lock.json` |
| `…/linear-local-agents/<codex\|claude>/.env` | Linear OAuth app credentials, port, public URL (mode 600, never in git) |
| `…/<name>/config.json` | routing from the template **plus** Cyrus's own Linear token store |
| `…/<name>/workspaces/<ISSUE>/` | one worktree per issue |
| `…/<name>/user-skills-plugin/skills/` | skills this agent carries into every repository |
| `…/<name>/startup.log` | service log |
| `~/Library/LaunchAgents/com.junwei.linear-local-agents.<name>.plist` | generated by `deploy.sh` |

Ports: codex 3456, claude 3457. Linear reaches them through Tailscale
Funnel paths `/codex` and `/claude` on this machine's tailnet hostname.

## Routing

Cyrus picks the repository in this order: `[repo=name]` tag in the issue
description → routing label → Linear project name (`projectKeys`) → team
(`teamKeys`). The project table is not hand-kept: `sync-routing.mjs`
generates it from Linear, where **an engineering project carries a link to
its GitHub repository** (Project → Resources). The script maps every
project of the bridge's teams to `~/repo/<repo>` (cloning with `gh` when
missing), reads the remote's default branch, applies the label procedures
from `engineeringDefaults` in `config.template.json`, and writes the
instances' `config.json`, which Cyrus reloads without a restart. A project
without a link routes only if its name is a directory under `~/repo/`;
otherwise it is unroutable and the bridge says so on the issue instead of
delegating. Renames are harmless: the table is rebuilt from current names
on every Project webhook and every `deploy.sh`. The last table lives in
`~/.local/share/linear-local-agents/routing.generated.json`. So a new
repository means: create the Linear project with its GitHub link. Only
`chile-ops` (routed by team `SAO`) is a static entry in the template.

Labels choose the procedure per repository: `Bug` → debugger,
`Feature`/`Improvement` → builder, `RFC` → scoper (read-only). An issue
without one of these is classified from its content. `[agent=codex|claude]`
or `[model=…]` in the description overrides the instance's default runner.

Skills the agents see: the repository's own `.claude/skills/` (both
runners; Cyrus symlinks them for Codex), the instance's
`user-skills-plugin/`, Cyrus's built-in implementation / debug /
investigate / verify-and-ship / summarize, and for Claude everything under
`~/.claude/skills`.

## Browser

`run.sh` sets `CYRUS_BROWSER_USE_ENABLED=true` and puts the runtime's
`node_modules/.bin` on `PATH`, so both runners are told they can drive
`agent-browser` (a Playwright CLI pinned in `runtime/package.json`) against a
local Chromium for UI verification, screenshots and bug reproduction. The
browser itself is downloaded once per machine with `agent-browser install`
(lands in `~/.agent-browser/`); `agent-browser doctor` checks it. Logging in
to production systems and any write there stays a human action.

Both runners drive it (verified 2026-09-26: each attached a homepage
screenshot within minutes). Codex needs `patches/codex-sandbox-mode.sh`:
Cyrus 0.2.72 starts every Codex thread in Codex's `workspace-write` seatbelt
with no config key to relax it, and Chrome cannot launch in there whatever
the writable roots (checked with `codex sandbox`); the patch makes the mode
follow `CYRUS_CODEX_SANDBOX_MODE`, which `run.sh` sets to
`danger-full-access`, the same footing the Claude runner already has.
`deploy.sh` re-applies every `patches/*.sh` after `npm ci`. Codex's own
"Browser use" (the ChatGPT app's `node_repl` MCP server in `~/.codex`) asks
permission per URL and is auto-denied unattended, so the Agent guidance tells
agents to use `agent-browser` instead.

## Bridge

Linear opens an agent session only for actions a human takes; the same
delegation or @mention made by an agent only sends a notification. `bridge/`
is a third launchd service (port 3458, Funnel path `/bridge`) that receives
the workspace's Issue webhooks and repeats the missing human action as the
workspace owner, using the owner's personal API key:

- an issue in a configured team gets a label listed in `bridge.json`
  `labelTriggers` → it is delegated to that agent (so `Development` starts
  Codex本机);
- an agent creates a sub-issue and delegates it (orchestrator mode) → the
  bridge @mentions the delegate so the child session actually starts;
- a pull request gets attached to an issue that carries a trigger label →
  the bridge @mentions the reviewer (`review` in `bridge.json`), whose
  prompt says to open its verdict with `@codex1` only when there are
  blockers;
- an agent posts a top-level comment that opens with `@<other agent>` → the
  bridge repeats that mention as the owner (`relay`), which is how review
  findings reach the coder;
- a human's new issue lands in Triage → the bridge @mentions the triage
  agent (`triage`), which runs the read-only `triage` skill;
- a project is created or updated → the bridge runs `sync-routing.mjs`
  (debounced), so the routing table follows renames and new links;
- a label or triage rule hits an issue whose project has no repository →
  one `[bridge:noproject]` comment explains what to attach, nothing else.

The webhook therefore subscribes to `Issue`, `Comment`, `Attachment` and
`Project` events. One label is the only click: label → implement → PR →
review → fix → CI, then a human merges.

Every action leaves a `[bridge:<rule>]` comment on the issue, which is also
the idempotency check, so silence on an issue means the bridge did not act.
The bridge keeps no other state; if it is down, the human click it replaces
still works. Secrets live in `…/bridge/.env` (`bridge/env.template`); the
webhook itself is created once with `webhookCreate` (resource type `Issue`,
all public teams, url `<funnel host>/bridge`, the same secret).

## Day to day

```sh
shared/linear-agents/deploy.sh           # after editing the template or bumping the lockfile
shared/linear-agents/service.sh status codex
shared/linear-agents/service.sh log claude
shared/linear-agents/service.sh restart codex   # only when no session is running
```

The machine must be awake and online: Linear retries a failed webhook three
times (1 min, 1 h, 6 h) and then drops it, so work delegated while the
machine sleeps has to be re-delegated.

## New machine

1. Clone dotfiles, install Node ≥ 20, sign in to `codex`, `claude` and `gh`
   (`gh auth setup-git` if the remotes use HTTPS), clone the repositories
   listed in `config.template.json` under `~/repo/`.
2. `deploy.sh` — installs the runtime and writes `config.json`; it warns
   that `.env` is missing.
3. Expose the ports: `tailscale funnel --bg --set-path /codex 3456` and
   `--set-path /claude 3457`; confirm with `tailscale funnel status`.
4. In Linear **Settings → API → OAuth applications**, point each app's
   callback (`<base URL>/callback`) and webhook (`<base URL>/linear-webhook`)
   at the new hostname. Create `…/<name>/.env` from `env.template` with that
   app's client id, secret and webhook secret.
5. Obtain the agent token into `config.json`:
   `node ~/.local/share/linear-local-agents/runtime/node_modules/cyrus-ai/dist/src/app.js --cyrus-home ~/.local/share/linear-local-agents/<name> --env-file …/<name>/.env self-auth-linear`
6. `deploy.sh --restart`, then mention the agent on a test issue.
